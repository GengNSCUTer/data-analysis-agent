## 0. 先分清两条链路

```text
生产数据分析 Agent
用户问题
-> QuestionRouter
-> Semantic Catalog / QueryPlan
-> Vanna + SiliconFlow 候选 SQL
-> SqlPolicy
-> PostgreSQL readonly role
-> ResultContract / ResultValidator / ChartContract
-> 前端表格、图表、证据与审计

离线后训练研究
Spider question + SQLite schema
-> Qwen2.5-Coder-1.5B Base 或 LoRA Adapter 候选 SQL
-> SQLite diagnostics / Test Suite / bounded denotation
-> Olist PostgreSQL protected holdout 迁移评测
```

两条链路的共同点是“模型可以提出候选 SQL”；区别是，生产链路具有数据库权限、安全策略和业务结果合同，离线研究没有。当前 Adapter 只属于后者，不能作为生产执行决策者。

## 1. 候选 SQL、权限和业务正确性

### 问题 1：后训练模型与 SiliconFlow 模型各自负责什么？为什么不能直接决定 PostgreSQL 是否执行？

**结论：** 二者在这个产品中都只能担任候选 SQL 生成器。候选并不等于获准执行的 SQL。

| 层级 | 责任 | 不能替代的部分 |
| --- | --- | --- |
| Qwen Base / LoRA Adapter | 离线生成候选 SQL，供研究对照。 | 不拥有生产数据库连接或权限。 |
| Vanna + SiliconFlow | 在生产运行时根据服务器提供的上下文调用 SQL 工具。 | 不决定安全、口径或结果是否可信。 |
| `SqlPolicy` | AST 级只读、单语句、对象/列范围、LIMIT 等确定性检查。 | 不证明业务指标口径正确。 |
| PostgreSQL reader role | 数据库真实权限、只读事务、超时与方言执行。 | 不证明返回值回答了问题。 |
| `ResultValidator` / `ResultContract` | 核对列、指标、时间范围、行数、结果形态。 | 不代替 SQL 安全策略。 |

代码证据：

- [`CandidateSqlContext`](../../../src/data_analysis_agent/candidate_sql_generator.py) 只允许服务器提供的问题、Catalog、QueryPlan、结果列合同进入候选模型；
- [`require_database_route()`](../../../src/data_analysis_agent/candidate_sql_generator.py) 对非数据库路由直接禁止 SQL 生成；
- [`chat_runtime.py`](../../../src/data_analysis_agent/chat_runtime.py) 只有 `route.should_generate_sql` 为真时才创建 QueryPlan 并进入 SQL 工具；
- [`postgres_runner.py`](../../../src/data_analysis_agent/postgres_runner.py) 先执行 `policy.evaluate()`，后用 reader role 执行，最后调用 `result_validator.validate()`。

**面试表述：**

> 我把 Text-to-SQL 模型限制为候选生成器。候选 SQL 必须连续通过 AST Policy、PostgreSQL 只读账号与 ResultContract 校验，模型不拥有执行权，也不承担指标口径的最终裁决。

### 问题 2：为什么不能把 Spider `dev` 的 gold SQL 放入训练？gold SQL 本身能不能用于 SFT？

**结论：** gold SQL 作为训练集的监督目标是必要的；把评测集的 gold SQL 混进训练，或在推理/评测时作为模型输入，才是数据泄漏。

正确的 SFT 样本是：

```text
模型输入：question + schema + ### SQL
监督目标：gold SQL + EOS
```

正确的评测输入是：

```text
模型输入：dev question + dev schema + ### SQL
模型看不到：dev gold SQL、结果行
```

需要避免的三类泄漏：

1. 将 `dev` / `test` 的 `question -> gold SQL` 加入训练集；
2. 评测 prompt 包含 gold SQL，变成“已知答案续写”；
3. train、validation、test 在同一 schema 或高度重复模板上混杂，使评测主要衡量记忆而不是泛化。

`teacher forcing` 会让训练时模型看见 gold SQL 的前缀以预测下一个 token，这是 decoder-only SFT 的标准做法，不等于评测泄漏。它也正是“validation loss 不能代替自由生成评测”的原因。

代码证据：[`generate_post_training_text_to_sql.py`](../../../scripts/post_training/inference/generate_post_training_text_to_sql.py) 的 `require_dev_cases_without_gold()` 只读取 `db_id` 和 `question`，不读取 `query`；gold SQL 仅在生成输出冻结后进入 denotation 审计。

### 问题 3：`schema-disjoint` 是什么？

**结论：** `disjoint` 表示不重叠。Spider 中同一个 `db_id` 的所有问题共享一套表、列和外键，因此一个数据库只能整体归入 train 或 validation。

```text
错误的随机按行切分：
train       = db_a 的问题 1、2、3
validation  = db_a 的问题 4、5

正确的 schema-disjoint 切分：
train       = db_a、db_b、db_c 的全部问题
validation  = db_d、db_e 的全部问题
```

随机按行切分会让验证集模型提前见过数据库表结构、字段命名和外键关系，从而高估泛化。当前还审计了归一化 SQL shape 重叠，防止不同数据库的近重复结构被误当成强泛化。

代码证据：[`split_post_training_candidates.py`](../../../scripts/post_training/data/split_post_training_candidates.py) 用 `db_id()` 取分组标识，再断言 `train_db_ids` 与 `validation_db_ids` 没有交集。

### 问题 4：`read_only_explain()` 通过说明什么？

**结论：** 它只说明给定 SQL 能在对应 SQLite 数据库以只读方式完成基本解析、名称解析和查询计划生成；它不证明 SQL 的业务语义正确。

该函数实际执行：

```python
sqlite3.connect("file:... ?mode=ro", uri=True)
connection.execute("PRAGMA query_only = ON")
connection.execute("EXPLAIN QUERY PLAN " + sql)
```

它可以发现：拼写错误、表/列不存在、部分基本 SQL 结构错误。它不能发现：

- GMV 是否使用了正确的支付状态、时间字段和退款规则；
- join 是否造成订单金额重复累计；
- 返回列是否覆盖本轮 QueryPlan；
- SQL 是否应在 PostgreSQL、而不是 SQLite 中运行；
- 当前用户是否有权访问对象；
- 结论是否有足够数据证据。

因此，SQLite `EXPLAIN`、AST Policy、PostgreSQL readonly role 和 ResultValidator 是互补层，而非重复检查。

## 2. Tokenizer、labels 和 forward smoke

### 问题 5：为什么 prompt 的 `labels` 要填 `-100`？

**结论：** Prompt 是条件上下文，不是我们的训练目标。`-100` 是 PyTorch/Transformers 交叉熵的 ignore index，表示这些位置仍可被 attention 使用，但不计入 loss。

```text
目标：给定 question + schema，生成 SQL
不是：复述 question + schema
```

如果 schema、字段说明和问题也参与 loss，长 prompt 会占据大量训练信号，模型会被额外激励去复述上下文，而不是把优化重点放在 SQL 续写上。

### 问题 6：`input_ids` 和 `labels` 分别负责什么？

以 `prompt_ids=[10,11,12]`、`target_ids=[20,21,22]`、`EOS=2` 为例：

```text
input_ids = [10, 11, 12, 20, 21, 22, 2]
labels    = [-100, -100, -100, 20, 21, 22, 2]
```

- `input_ids`：送入模型的完整 token 序列；
- `labels`：指出哪些位置应该预测并计 loss；
- decoder-only causal LM 在内部做位置错位，学习“已有前缀 -> 下一个 SQL token”。

代码证据：[`CausalSqlDataset`](../../../scripts/post_training/training/run_post_training_sft_smoke.py) 将 prompt、target 和 EOS 拼接，并为 prompt 构造 `-100` mask；`CausalSqlCollator` 用 pad token 补齐输入、用 `0` 补齐 attention mask、用 `-100` 补齐 labels。

### 问题 7：为什么在 SQL 后加入 `eos_token_id`？

EOS 是“输出已结束”的可学习信号。它帮助模型在生成完整 SQL 后自然停止，减少继续输出 Markdown、解释、第二条 SQL 或无关文本的概率。推理时生成器也可在采样到 EOS 后结束；否则只能依赖 `max_new_tokens` 强制截断。

### 问题 8：为什么 forward smoke 得到了 loss 也不等于模型完成微调？

Forward smoke 的目标是检查：数据可读、tokenizer 可用、label layout 正确、基座/LoRA 能加载、loss 有限。它明确使用：

```python
with torch.no_grad():
    output = model(**batch)
```

因此没有：

```text
loss.backward()
optimizer.step()
LoRA 参数更新
adapter 保存
```

即便正式训练的 loss 下降，也只表示训练分布中 gold SQL token 的平均负对数似然下降；它不能直接证明自由生成、SQL 执行、结果等价、Olist 业务口径或生产安全性提升。

## 3. SFT、梯度累积、学习率与数据集划分

### 问题 9：为什么 `batch_size=1` 却每 4 条样本才更新一次？

当前配置：

```text
per_device_train_batch_size = 1
gradient_accumulation_steps = 4
effective batch size = 4
```

真正 batch 为 4 时，4 条样本会一起进入 GPU 完成一次 forward/backward；显存不足时，梯度累积用 4 次串行 micro-batch 近似这一更新效果：

```text
第 1 条：forward -> backward -> 累积 .grad
第 2 条：forward -> backward -> 累积 .grad
第 3 条：forward -> backward -> 累积 .grad
第 4 条：forward -> backward -> optimizer.step() -> zero_grad()
```

它节省激活同时驻留的显存，代价通常是比真正 `batch=4` 更慢。当前 3,048 条 train 数据、2 epoch 的计算是：

```text
3,048 / 4 = 762 optimizer steps / epoch
762 * 2 = 1,524 optimizer steps
```

### 问题 10：为什么不能在每个 micro-batch 前 `zero_grad()`？

PyTorch 默认把梯度累加在参数 `.grad` 中。如果每个样本前清空，前 3 个样本的梯度会丢失，最终等价于 effective batch 为 1。正确行为是在新累积窗口开始前或完成 `optimizer.step()` 后清空，保留 4 个样本共同形成的更新方向。

一次真正更新的最小流程是：

```text
forward -> loss -> backward -> optimizer.step() -> scheduler.step() -> zero_grad()
```

其中 `backward()` 计算可训练参数的梯度，`optimizer.step()` 才实际改写 LoRA 参数。

### 问题 11：`learning_rate=1e-4` 控制什么？

学习率控制优化器更新的基础尺度，不代表“每个参数固定加减 0.0001”。最简单的梯度下降近似为：

```text
parameter_new = parameter_old - learning_rate * gradient
```

当前使用 `paged_adamw_8bit`。AdamW 还会结合一阶/二阶梯度统计、bias correction、可能的 weight decay、梯度裁剪和 scheduler，因此实际更新量是自适应的。

### 问题 12：validation 和 test 有什么区别？为什么最后一次 train loss 不是最佳 checkpoint 的依据？

| 数据角色 | 是否参与参数更新 | 用途 | 能否反复用于调参 |
| --- | --- | --- | --- |
| train | 是 | `backward()` 与 `optimizer.step()`。 | 是。 |
| validation | 否 | 监控过拟合、选择 epoch/学习率/checkpoint。 | 可以，但会参与决策。 |
| test | 否 | 方案冻结后的最终无偏报告。 | 原则上不应反复用于调参。 |

当 `train loss` 继续下降而 `validation loss` 上升，通常是过拟合：模型越贴合训练样本，越不适合未见样本。优先应选 validation 最低的 checkpoint、考虑 early stopping/减少 epoch/检查学习率和数据质量，再讨论数据规模。

当前脚本会周期性 eval/save，但没有设置 `load_best_model_at_end=True` 与 `metric_for_best_model="eval_loss"`，所以 `adapter_final` 是最后一步结果，不保证是 validation 最优 checkpoint。这个改进应放在领域数据设计之后，并通过固定实验合同验证，而不是直接修改并宣称变好。

当前项目的不同评测角色：

```text
Spider train 派生 3,048 / 552 schema-disjoint split -> 训练与 validation
官方 Spider dev 1,034 条 -> 独立的 test-like 离线候选质量评测
Olist 12 条 protected holdout -> 当前产品领域迁移子门
```

## 4. LoRA、QLoRA 和 Adapter 生命周期

### 问题 13：基础 Qwen 参数冻结后，为什么仍然参与 forward？

一个原始线性层可写为：

```text
y = xW
```

挂载 LoRA 后为：

```text
y = x(W + DeltaW)
DeltaW = (alpha / r) * B * A
```

因此基础权重 `W` 仍完成主要计算；冻结只表示 `W.requires_grad=False`，不表示前向时不用它。训练和推理都使用“Qwen 基座 + Adapter”。只有训练中 LoRA 的 `A/B` 参数获得梯度并被优化器更新；推理没有 `backward()` 和 `optimizer.step()`，所以任何参数都不更新。

### 问题 14：A、B 矩阵为何能减少参数？

若原始线性层：

```text
W: d_out x d_in
```

LoRA 不是训练完整 `DeltaW`，而是：

```text
A: r x d_in
B: d_out x r
DeltaW = B * A
```

全量更新参数数目是 `d_out * d_in`；LoRA 为 `r * (d_in + d_out)`。例如 `4096 x 4096` 的层，rank `16` 时约从 16,777,216 个参数降为 131,072 个。`A` 可理解为把输入映射到低秩空间，`B` 再映射回输出空间；两者共同构造可学习的低秩增量，并不是两份独立知识库。

### 问题 15：为什么同时适配 attention 和 MLP？

当前 `target_modules` 包含：

```text
attention: q_proj, k_proj, v_proj, o_proj
MLP:       gate_proj, up_proj, down_proj
```

- attention 投影主要影响 token 间的信息交互，例如中文问题、表名、列名、聚合条件和 join 关系的对齐；
- MLP 投影主要影响隐藏表示的非线性语义变换与 SQL token 的生成模式，例如聚合、过滤、排序和方言结构。

同时适配提升表达容量，但也增加可训练参数、显存和小样本过拟合风险。

### 问题 16：rank 从 `r=16` 提升到 `r=64` 会怎样？

rank 增大 4 倍时，LoRA 参数和相关优化器状态大约也扩大 4 倍。可能收益是更高的领域适配容量；可能代价是更多显存和计算、更高过拟合风险、更明显的生成行为漂移。当前应先建立领域对齐训练/验证集，并以 `r=16` 作为基线；只有在数据足够、validation 仍显示欠拟合时，再把 rank 作为一个可控变量进行对照。

### 问题 17：`from_pretrained()`、`prepare_model_for_kbit_training()`、`get_peft_model()`、`PeftModel.from_pretrained()` 和 `trainer.train()` 分别做什么？

```text
AutoModelForCausalLM.from_pretrained()
    加载 Qwen 基座；bf16 或 4-bit 只决定冻结基座的存储形式。

prepare_model_for_kbit_training() [仅 QLoRA]
    为已经 4-bit 加载且冻结的基座准备稳定的 adapter 训练路径；不创建/更新 LoRA。

get_peft_model()
    在目标层注入新初始化、尚未训练的 LoRA A/B 矩阵，并设置其可训练。

trainer.train()
    真正执行 forward、loss、backward、optimizer step、validation、checkpoint；更新 LoRA 参数。

PeftModel.from_pretrained()
    推理或评测时，把磁盘中已训练的 adapter_model.safetensors 重载到相同的基础 Qwen 上。
```

**重要区分：** 仅用 4-bit 加载模型，解决的是显存问题，不会产生新的 SQL 能力；只有注入 LoRA、构造监督目标并执行训练更新，才构成 LoRA/QLoRA SFT。

### 问题 18：`bf16_lora` 与 `qlora_4bit` 是两个任务吗？

不是。二者是同一 Text-to-SQL SFT 任务的两条资源路径：

| 模式 | 冻结基座表示 | 计算 | 实际更新参数 |
| --- | --- | --- | --- |
| `bf16_lora` | bfloat16 | bf16 | LoRA A/B |
| `qlora_4bit` | 4-bit NF4 | 主要 bf16 | LoRA A/B |

当前 1.5B 模型在 24GB 4090/3090 上可以运行 bf16 LoRA，因此 v2 主实验采用 bf16。QLoRA 是显存更紧张或基座更大时的备选路径，不是天然更高级、更准确的方式。

## 5. 当前实验判断与下一学习单元

已完成的有限证据：

```text
Spider/SQLite 固定协议：3,600 条 train-only 数据训练的 bf16 LoRA Adapter
在 1,034 条独立 dev 对照中优于 matching Base。

Olist/PostgreSQL protected holdout：12 条，Adapter 没有迁移收益。
Base -> Adapter：ResultContract valid 2 -> 0。
```

因此当前不能继续把“更多通用 Spider 数据”当作默认解决方案，也不能把 Adapter 接入 Vanna/SiliconFlow 的默认生产模型。下一学习单元不是立即训练，而是先审查**领域对齐数据合同**：

1. 为什么现有 12 条 protected Olist holdout 绝不能放入训练；
2. 中文问题到 PostgreSQL SQL 的样本为何还需要 Semantic Catalog、QueryPlan、ResultContract；
3. 如何设计独立的 Olist train/validation/test，而不让评测数据回流训练；
4. 如何把多指标、时间过滤、去重、归因、join 粒度和澄清问题做成通用训练/评测维度，而非为单一数据集硬编码。

在用户复述并确认上述设计后，才可以创建领域数据模板、最小合成 fixture 或启动新的训练任务。

## 6. 学习单元二：Olist/PostgreSQL 领域对齐数据合同

本单元不创建任何 Olist 训练样本，也不修改当前 Adapter。目标是解释：为什么 Spider 的 SQL
候选质量提升没有直接迁移，以及之后如何准备“模型真正看得懂当前业务上下文”的数据，而不污染
测试结论。

### 问题 19：为什么现有 protected holdout 即使领域数据稀缺，也绝不能进入训练？

**结论：** 因为它是测试集，不是可自由补充的数据池；“样本太少”不能成为打破隔离的理由。

`evals/manifests/post_training_holdout_v1.yaml` 把项目 v2 的 60 条 golden 永久隔离，当前
Olist 候选迁移评测只从其中选择 12 条可回答、需要数据库的 case。它们禁止直接训练、同义改写、
few-shot 示例、偏好对构造和人工照着改写。否则模型会提前见过相同的指标组合、Join 图、结果别名
或语义模板；即使不复制相同 SQL，测试也无法再证明新问题上的泛化能力。

这里需要区分两种切分逻辑：Spider 有很多数据库，按 `db_id` schema-disjoint；Olist 是一个固定
业务工作区，模型本来就会看到同一套 schema，因此不能要求 Olist schema-disjoint。Olist 应改按
问题改写族、指标/维度/归因组合、Join 图、SQL 形状、时间模式和 Catalog 快照分组切分。已有 60 条
及其任何派生表达始终只属于 test/holdout。

### 问题 20：为什么“中文问题 -> PostgreSQL gold SQL”仍不够？

**结论：** 它只给出输入和答案，没有给出答案依赖的业务前提。模型会学 SQL 形式，却不知道
指标定义、允许的维度归因、Join 粒度、所需别名和本轮结果合同从哪里来。

当前运行时不是将用户问题直接交给模型。`QuestionRouter` 先决定是否应该查库；
`Semantic Catalog` 提供可见指标、表、列、Join 和归因规则；`QueryPlan` 固化本轮指标、维度、
时间、聚合策略和 required result columns；`ResultContract` 再冻结版本、结果别名、时间和归因
要求。只有这一组服务器拥有的上下文，加上问题，才被
`CandidateSqlContext` 渲染为候选 SQL 模型的输入。

因此领域 SFT 的**输入**应是“问题 + 服务器版本化 Catalog slice + QueryPlan + SQL-only 输出合同”，
**监督目标**仍是 gold SQL 和 EOS。模型不学习获得权限或放松安全规则；`SqlPolicy`、PostgreSQL
reader role 和 `ResultValidator` 继续在模型之后独立执行。

### 问题 21：一条可复用的领域训练样本应包含什么？

以“按品类统计 GMV、有效订单数和好评率”为例，除问题和 SQL 外，至少记录：

| 字段族 | 最小内容 | 用途 |
| --- | --- | --- |
| 可追溯性 | `sample_id`、source、license、标注/复核时间 | 说明样本从哪里来、能否复现。 |
| 工作区快照 | `workspace_id`、dataset/catalog/metric/policy version、角色范围 | 防止把不同口径或权限下的 SQL 混在一起。 |
| 受控输入 | `question_redacted`、必要 `working_memory`、Catalog slice | 让模型知道可用表列、指标与上下文，不保存不必要原文。 |
| 路由与计划 | `target_route`、`query_plan`、required result columns、维度归因要求 | 明确是否应该生成 SQL、结果粒度和必须返回的字段。 |
| 监督与证据 | `candidate_sql`、SQL 方言、只读执行/合同状态、review provenance | 确认 target 是可执行且经复核的候选，而不是未验证模型输出。 |
| 隔离信息 | `split`、semantic family、SQL shape/join family、template family | 防止改写题和同一业务口径跨 train/validation/test 泄漏。 |

对于当前**候选 SQL Adapter**，只有 `route.should_generate_sql=true` 的 answerable database
样本进入 SQL SFT；澄清、定义解释和拒答案例应保留为路由/端到端评测资产，或在未来单独训练
路由/对话头，不能强行让 SQL generator 对所有问题都输出 SQL。

### 问题 22：Olist 领域数据最少应该有几千条吗？大规模构建难度如何？

**结论：** 不应先把“几千条”当作硬门槛。对 1.5B LoRA，真正稀缺的是经 Catalog、QueryPlan、
PostgreSQL 执行和 ResultContract 复核后的**独立业务语义样本**，不是用同一模板换措辞得到的行数。

建议把规模理解为三个受控阶段，而不是一次性造 3,000 条：

| 阶段 | 数据规模建议 | 目的 | 不能得出的结论 |
| --- | --- | --- | --- |
| 数据合同试点 | 0 条训练数据 | 审查字段、版本、隔离、检查器和覆盖矩阵。 | 不能训练或评价模型。 |
| 小型领域 pilot | 约 300--500 条语义独立 train，约 80--150 条独立 validation | 验证数据构造、prompt 与 LoRA 是否在领域验证集上有正向信号。 | 不能声称业务全面泛化或替换线上模型。 |
| 扩展实验 | 约 1,000--2,000 条语义独立 train，约 150--300 条 validation | 覆盖多指标、时间、去重、Join、归因、别名与复杂查询，并和 matching Base 对照。 | 若 protected holdout 无提升，不能靠继续堆数量宣称成功。 |

只有错误分析表明覆盖不足、且小型 pilot 的 train/validation/holdout 都没有出现明显过拟合时，
才讨论 2,000--3,000 条。3,000 条几乎相同的改写通常比 500 条覆盖不同业务语义的样本更差：它会
放大模板记忆，给 validation 带来虚高分数，也无法修复当前 Olist 的 alias、事实粒度、归因和
多指标错误。

大规模构建的难点不在于“让模型或脚本写出很多 SQL”，而在于每条样本都要证明：使用的是正确的
Catalog 版本、没有越权、指标口径与 Join 粒度正确、结果列满足合同、没有与 60 条 holdout 同族，
并且其来源/许可证可追溯。可用 Catalog 驱动的覆盖矩阵和确定性 SQL 模板减少人工劳动，再做
受控中文改写和人工复核；不能直接把未验证的 LLM 生成 SQL 批量当作 gold，也不能通过大量同义改写
伪造样本规模。

**当前决定：** 先设计数据合同和覆盖矩阵；未获得用户确认前，不创建数据模板、不生成样本、不
启动训练。下一学习单元应先共同设计“领域样本覆盖矩阵”，再决定是否进入小型 pilot。

### 下一学习单元预告

下一次只阅读 `prepare_model_for_kbit_training()` 这一处调用，暂不进入 `get_peft_model()`。
重点理解它为什么只在 QLoRA 路径执行、它对冻结基座和梯度检查点做了什么，以及为什么它本身仍不等于
“已经开始训练”。

### `prepare_model_for_kbit_training()` 用户复述与补充

1. 用户正确指出：LoRA 通过额外 adapter 学习任务能力，不直接更新基座权重。需要补充的是，LoRA
   在推理时形成有效权重 `W0 + BA`，所以它会改变模型输出行为，只是冻结的 `W0` 本身不被物理改写。
   QLoRA 不训练 4bit 基座的直接原因是这类量化权重不适合常规高精度优化器直接更新；若全量更新，
   需要保存/维护高精度状态并反复量化，显存与数值成本会显著上升。训练很小的 A/B adapter 矩阵能
   以低成本保留基座、独立保存和可回退。
2. `input_ids` 是整数索引，不能也不会有梯度。`enable_input_require_grads()` 处理的是 embedding 查表
   后的浮点输出 `x`，不是 token id。本脚本的 QLoRA 配置在 PEFT 中启用重入式 gradient checkpointing：
   checkpoint 区段至少要有一个需要梯度的输入，反向时才会重新执行并建立图；令 `x.requires_grad=True`
   能使 checkpoint 内的 LoRA 参数获得梯度。`x` 不是 optimizer 更新的模型参数，计算出的 `dL/dx` 仅为
   保持反向路径，训练后会丢弃。
3. 用户正确指出该函数尚未创建 LoRA 参数或开始训练；它只冻结已加载基座、做 k-bit 训练准备并启用
   梯度检查点。当前 PEFT 实现会把非 `Params4bit` 的 fp16/bf16 参数转为 fp32，实际范围比旧 docstring
   所说的 LayerNorm/lm head 更宽。原因是低精度会增大舍入误差：LayerNorm 的均值/方差计算包含相近数
   的相减和小方差除法，误差可能被放大；输出 logits 随后的 softmax/交叉熵也含大数累积、指数和归一化，
   更容易出现精度损失、无穷值或 NaN。4bit 基座 `Params4bit` 保持量化，其他敏感浮点状态提升到 fp32，
   是显存和稳定性的折中。

**审阅观察：** `prepare_model_for_kbit_training()` 这里未显式传入 checkpoint 参数，PEFT 初始按默认重入式
路径准备；后面的 `TrainingArguments` 则请求 `use_reentrant=False`。两者最终通常兼容，提前设置的输入梯度
也仍是安全的，但配置语义不够一致。后续进入训练参数审阅时应将两处统一，并用最小 forward/backward
回归验证；当前不在学习阶段顺带修改它。

### 梯度检查点用户复述结果

- 普通训练保存中间激活，是为了反向传播时直接使用这些值计算梯度。
- 梯度检查点通过把连续层划成 checkpoint 区域，少保存区域内部激活，反向时重新执行该区域来恢复计算图，
  以计算换显存；“把几个地方合在一起”只是区域划分的表面现象，不是它节省显存的根本原因。
- 如果 checkpoint 区域没有可求梯度的输入，重入式 checkpoint 可能不建立有效的 autograd 路径，导致区域内
  的 LoRA 参数拿不到梯度。
- `enable_input_require_grads()` 作用于 embedding 输出的浮点梯度路径，而不是整数 `input_ids`；真正由
  optimizer 更新的是 LoRA adapter 参数。

## 10. 学习单元五：`get_peft_model()` 与 LoRA 配置

当前代码入口是 `run_post_training_sft_smoke.py:394-404`：

```python
model = get_peft_model(
    model,
    LoraConfig(
        r=args.lora_r,
        lora_alpha=args.lora_alpha,
        lora_dropout=args.lora_dropout,
        bias="none",
        target_modules=["q_proj", "k_proj", "v_proj", "o_proj", "gate_proj", "up_proj", "down_proj"],
        task_type="CAUSAL_LM",
    ),
)
```

### 它做什么

`get_peft_model()` 接收已经加载并准备好的基座模型，以及一份 `LoraConfig`，返回一个被 PEFT 包装过的模型。
它会在匹配的线性层旁注入 LoRA 的 A/B 低秩矩阵，将基座参数保持冻结，并把 adapter 参数标记为可训练。此时
“可训练参数集合”才真正出现，但仍然没有执行 forward、backward 或 optimizer step。

### 配置逐项对应

- `r` 是低秩矩阵的 rank。rank 越大，adapter 容量越大、可训练参数和显存也越多；不是训练轮数。
- `lora_alpha` 是缩放系数，实际增量通常按 `alpha / r` 缩放。它不是学习率。
- `lora_dropout` 只在训练时对 LoRA 分支做 dropout，降低小数据过拟合风险；推理时关闭。
- `bias="none"` 表示不额外训练目标层 bias，进一步限制可训练范围。
- `target_modules` 决定哪些模块注入 adapter。本脚本覆盖 Qwen/Llama 风格注意力投影和 MLP 投影：
  `q/k/v/o_proj` 属于注意力，`gate/up/down_proj` 属于前馈网络。它依赖模型实际模块命名，不能对任意模型无条件保证匹配。
- `task_type="CAUSAL_LM"` 告诉 PEFT 这是因果语言模型任务，使用适合自回归生成的包装方式。

当前脚本注入 LoRA 后调用 `count_parameters()`，用于记录可训练参数占总参数的比例；这只能证明参数集合配置正确，
还不能证明这些参数经过反向传播后真的更新，也不能证明 SQL 质量提升。

### 用户复述结果

1. LoRA A/B 是低秩矩阵，训练参数量约为 `r * d_in + d_out * r`，明显少于直接更新完整的
   `d_out * d_in` 权重矩阵。
2. `r` 控制 LoRA 分支的容量/表达能力，不是学习率、训练轮数或 batch size。
3. `lora_alpha` 控制 LoRA 增量在有效权重中的缩放影响；学习率控制训练时每次参数更新的步长，
   两者作用位置不同。
4. `target_modules` 命名不匹配时，预期层可能没有被注入或只注入部分层，导致 adapter 参数为 0/过少，
   训练没有覆盖预期模块；因此必须检查实际注入结果和可训练参数数量。

## 11. 学习单元六：LoRA 注入后的 forward 与 loss（预告）

下一单元只追踪一个样本从 `input_ids` 到 `loss` 的路径：模型输出 `logits`、因果语言模型的错位预测、
`labels=-100` 如何被交叉熵忽略，以及为什么得到有限 loss 仍不能证明 SQL 正确。暂不讲 backward、
optimizer 或领域数据构造。

### 已完成：LoRA 配置复述

用户已正确复述本单元进入 `forward` 前必须掌握的四点：

1. LoRA 的可训练增量由低秩 A/B 矩阵构成。对于输入维度 `d_in`、输出维度 `d_out` 的目标线性层，
   参数量约为 `r * d_in + d_out * r`，而不是完整 `d_out * d_in`；它以较小参数量近似任务所需的
   更新方向。
2. `r` 是 adapter 的 rank，控制低秩分支可表达的更新容量，而不是学习率或训练轮数。
3. `lora_alpha` 控制 LoRA 增量写入有效权重时的缩放，通常与 `r` 共同形成 `alpha / r`；学习率则在
   `optimizer.step()` 时控制 A/B 参数按梯度更新的步长，两者处于不同阶段。
4. `target_modules` 决定哪些真实线性层被 PEFT 注入 LoRA。模块名不匹配会造成未注入或只部分注入，
   因而必须通过可训练参数统计和 PEFT 注入结果检查，而不能只凭配置文本假设生效。

### 当前学习单元：一次 SFT `forward -> loss`

代码入口仍是
[`scripts/post_training/training/run_post_training_sft_smoke.py`](../../../scripts/post_training/training/run_post_training_sft_smoke.py)。
在 `get_peft_model()` 已返回“Qwen 基座 + LoRA adapter”之后，Trainer 才会把一个 batch 的
`input_ids`、`attention_mask`、`labels` 交给模型。此处尚未执行 `backward()` 或参数更新。

一条 decoder-only SFT 样本可简化为：

```text
prompt tokens + SQL token_1 + SQL token_2 + ... + EOS
labels: -100          -100          SQL token_1 ... + EOS
```

模型前向计算会为序列每个位置输出对整个词表的分数 `logits`。若 batch 大小为 `B`、序列长度为 `T`、
词表大小为 `V`，则 `logits` 形状是 `[B, T, V]`。因果语言模型将位置 `t` 的 logits 与位置 `t+1`
的 label 对齐：已看到前缀 token 时，模型学习预测下一个 token。Prompt 对应的 labels 虽为 `-100`，
prompt token 仍保持 `attention_mask=1`，因为 SQL 生成必须能注意到 schema、问题和指令；`-100` 只表示
该位置不产生监督 loss。

交叉熵会忽略所有 `labels=-100` 的位置，因此有效 loss 只监督 SQL 目标和真实 EOS。有限或下降的 loss

## 12. 学习单元七：`backward()` 只计算梯度

真实入口仍是 `run_post_training_sft_smoke.py:453` 的 `trainer.train()`。脚本没有显式书写
`loss.backward()`，因为 Hugging Face `Trainer` 在训练循环内部完成它。本单元只理解这一件事：

```text
forward 得到 loss
loss.backward()
-> autograd 按计算图和链式法则计算每个可训练参数的 d(loss)/d(parameter)
-> 将梯度写入 parameter.grad
```

对本项目而言，LoRA A/B 参数是 `requires_grad=True` 的可训练参数；冻结基座权重是
`requires_grad=False`。因此 backward 之后，LoRA A/B 获得 `.grad`，基座权重不会因为本次训练而获得
可供优化器更新的梯度。`loss` 是一个标量计算结果，不是需要被优化器直接改写的模型参数。

**关键边界：** `backward()` 只是计算和累积梯度，尚未改变 LoRA A/B 的数值；实际参数更新要等到下一单元的
`optimizer.step()`。在梯度累积时，连续多个 micro-batch 的 backward 会把梯度累加到同一组 `.grad` 上，直到
达到累积步数才更新并清空。

### 待用户回答：只回答这三题后再进入 `optimizer.step()`

1. `loss.backward()` 结束后，LoRA A/B 参数本身已经改变了吗？如果没有，什么东西发生了变化？
2. 为什么冻结的基座权重在 forward 中仍参与计算，却不应在本次 backward 后被优化器更新？
3. `loss` 是模型参数吗？`optimizer.step()` 真正读取并改写的分别是什么？

本单元不讨论 AdamW 公式、学习率调度、梯度裁剪或 checkpoint 保存；这些在用户复述后再逐一审阅。

### 2026-09-01：用户复述与纠正

1. 用户正确：`loss.backward()` 不会修改 LoRA A/B 参数值。更精确地说，它会计算梯度并写入
   `parameter.grad`；如果本轮梯度在 `zero_grad()` 后刚开始，这相当于产生新的 `.grad`，如果处于梯度累积
   窗口中，则将本 micro-batch 的梯度加到已有 `.grad` 上。
2. 用户正确：冻结基座权重仍承担主要 forward 计算。有效线性变换仍包含基座 `W0`，只是其

3. 用户正确：loss 是计算图得到的标量结果，不是模型参数。`optimizer.step()` 会读取每个可训练参数的
   `.grad`，并结合优化器内部状态（本脚本使用 AdamW 的相关状态）计算更新，最终改写 LoRA A/B 参数值。

## 13. 学习单元八：`optimizer.step()` 才更新 LoRA 参数

当前脚本把 `learning_rate`、`gradient_accumulation_steps` 和优化器类型交给 `TrainingArguments`
（`run_post_training_sft_smoke.py:419-432`）。其中 `optim="paged_adamw_8bit"` 表示 Trainer 内部使用
8-bit 状态存储优化器版本；本单元不展开 AdamW 公式，只建立参数更新时序。

```text
第 1 个 micro-batch: forward -> backward -> LoRA .grad
第 2 个 micro-batch: forward -> backward -> LoRA .grad 累加
...达到 gradient_accumulation_steps
optimizer.step() -> 读取 LoRA .grad 和优化器状态，改写 LoRA A/B
zero_grad()       -> 清空已使用的 .grad，开始下一轮累积
```

`optimizer.step()` 不读取 loss 来直接改参数；loss 已经通过 backward 转化为每个 LoRA 参数的梯度。它也不应
改写冻结基座，因为基座不在可训练参数组中且不带可更新梯度。即使使用 AdamW，最简化的直觉仍是“沿着让 loss
下降的方向小幅更新参数”；真实更新还会结合历史梯度统计、学习率和权重衰减。

### 2026-09-01：用户复述与纠正

1. 用户回答正确：`gradient_accumulation_steps=4` 的含义是在四个 micro-batch 的信息累计后，再进行一次
   参数更新。若每个 micro-batch 都调用 `optimizer.step()`，就会变为四次独立的 batch=1 更新，既破坏了
   预期的有效 batch=4，也会走出不同的优化轨迹。这里的“累计”不是把四条样本同时塞进显存，而是顺序执行
   四次 forward/backward，将它们的梯度累计起来，以时间换显存。
2. 用户暂时混淆是正常的；需要记住严格的数据流：

   ```text
   forward -> 得到标量 loss
           -> loss.backward()
           -> 每个可训练 LoRA 参数的 parameter.grad 被写入或累加
           -> optimizer.step()
           -> 读取 parameter.grad、优化器状态和 learning rate
           -> 改写 LoRA A/B 参数值
   ```

   因此 `optimizer.step()` 不直接读取标量 `loss`。`loss` 是 backward 计算梯度的起点；优化器实际拿到的是
   每个 LoRA 参数的 `.grad`。冻结基座没有可训练梯度，也不在优化器的参数组中，所以不会被此步骤改写。
3. 用户回答正确。更完整地说，不能在当前累积窗口的每次 backward 前清空梯度，否则前几个
   micro-batch 的信息会丢失；完成一次 `optimizer.step()` 后，必须清空刚被消费的 `.grad`，否则它会泄漏到
   下一轮累积。具体框架也可能在“上一次 step 刚结束”或“下一窗口第一次 backward 之前”调用
   `zero_grad()`；不变量是绝不能在同一累积窗口内部提前清空。
