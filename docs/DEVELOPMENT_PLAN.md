# Data Analysis Agent｜完整开发计划

> 状态：已冻结为开发前基线；本文件只规划工作，不代表功能已经实现。  
> 最近更新：2026-08-02

## 1. 计划目标与开发原则

项目目标是交付一个可演示、可解释、可评测的可信业务数据分析 Agent。用户用中文询问经营问题，系统在固定权限和只读数据范围内执行受控查询，返回结论、指标口径、最终 SQL、结果表、图表和审计证据。

开发顺序必须由风险和依赖决定，而不是由页面效果决定：先建立数据/指标合同，再建立数据库只读边界和 SQL 策略，再接入 Agent，最后构建前端体验。这样能避免“聊天框先能说话、但查询口径和安全性都不可信”的返工。

本计划使用“阶段门”而非日历日期。每个阶段只有达到退出条件，才进入下一阶段；后续可根据实际投入时间将每个阶段拆为一个或多个迭代。

## 3. 目标架构与责任划分

```text
浏览器（Next.js / TailAdmin）
  ├─ 经营概览、指标卡、历史、评测、管理页面
  └─ 智能分析页：封装 Vanna <vanna-chat>
                   │ HTTPS / SSE
                   ▼
FastAPI（Python）
  ├─ 身份、角色、工作区范围解析
  ├─ 指标与 Schema 上下文服务
  ├─ Vanna Agent 与受控 Tool Registry
  ├─ SQL AST Policy Gateway
  ├─ PostgreSQL 只读执行器
  ├─ 证据链、审计、评测服务
  └─ SSE API
                   │
                   ▼
PostgreSQL
  ├─ analytics：清洗后的事实表、维表、指标视图（只读角色）
  └─ app：用户、会话、审计、指标定义、数据集版本、评测（应用角色）
```

责任边界：

- **LLM/Agent** 负责理解问题、调用受控工具、生成候选 SQL 和语言总结，不拥有直接数据库权限；
- **指标语义层** 负责业务口径，不让模型根据表名自行猜测 GMV、取消率等定义；
- **SQL 策略层** 负责是否可以执行；其判断不能由模型替代；
- **数据库角色** 提供策略层外的最终只读防线；
- **证据层** 负责把“为什么得出该结论”变成用户和审计都能读取的结构化结果；
- **前端** 负责展示和交互，不自行拼装或绕过 SQL 安全规则。

## 4. 阶段计划与阶段门

### Phase 0｜立项、边界与开发计划（已完成）

**范围**：项目定位、MVP、技术选型、数据策略初稿、飞书/仓库同步规则、上游参考目录整理。

**交付物**：`PROJECT.md`、`AGENTS.md`、本开发计划、飞书项目文档、已推送的 GitHub 基线。

**退出条件**：自有仓库、上游参考与文档事实来源均无歧义；不开始数据分析、脚手架或业务功能。

### Phase 1｜领域与数据合同冻结

**目的**：在接入 Agent 前，先定义系统允许分析什么、每个指标到底是什么意思。

**任务**：

1. 从 Olist 主案例中选择 6–10 张可解释的原始表，定义原始层、清洗层和分析层的边界；
2. 编写数据集 manifest：来源、许可证、版本/下载日期、校验、署名、字段风险与禁止展示字段；
3. 编写数据字典：表、列、数据类型、主外键、业务含义、敏感性、可访问角色；
4. 冻结 8–12 个首批指标的精确定义、粒度、时间字段、默认过滤、允许维度和推荐图表；
5. 设计 `analytics` 和 `app` 的初版 ERD，以及组织/角色范围的最小演示模型；
6. 把 20 个代表性业务问题写成评测草案，并标注需要的指标、表和预期查询特征。

**交付物**：`data/manifest/`、`docs/data-dictionary.md`、`docs/metric-catalog.md`、`docs/architecture/data-model.md`、`evals/cases/draft.yaml`。

**退出条件**：每个核心指标都能由人工按数据字典写出明确 SQL；每个评测问题都有可解释的标准口径；不存在“让模型自己猜业务规则”的缺口。

### Phase 2｜可复现数据管道与数据库基线

**目的**：让数据、Schema、权限和本地运行方式可重复建立。

**任务**：

1. 建立 PostgreSQL 本地运行配置及 `analytics` / `app` Schema；
2. 创建分析查询只读角色和应用读写角色，验证权限不能互相越界；
3. 编写下载指引、原始数据导入、清洗/建模、加载和校验脚本；
4. 创建小型合成 fixture，保证 CI 和测试无需下载原始第三方数据；
5. 编写迁移、初始化和健康检查命令；
6. 为每个首批指标生成人工核验 SQL / golden 聚合结果。

**交付物**：`infra/`、`data/ddl/`、`data/transforms/`、`data/fixtures/`、`docs/runbooks/local-data-setup.md`、指标 golden 结果。

**退出条件**：新环境可仅凭仓库和数据下载说明重建数据库；只读角色无法写表；核心指标的人工基线可重复计算。

### Phase 3｜后端应用骨架与可观测性

**目的**：建立可测试的 FastAPI 服务与持久化模型，但不急于开放 Agent。

**任务**：

1. 创建 `backend/`，固定 Python 版本、依赖锁、代码质量和测试命令；
2. 建立配置模型、环境变量模板、日志格式、请求 ID、健康检查和错误码；
3. 实现应用数据库迁移：用户、角色、会话、指标、数据集、审计、评测表；
4. 定义认证抽象与本地演示身份，先提供 `analyst` / `admin` 的最小可验证差异；
5. 定义 API 响应模型、错误模型和 SSE 事件协议；
6. 为迁移、配置、鉴权占位和健康检查编写测试。

**交付物**：可启动 FastAPI、OpenAPI 文档、数据库迁移、`.env.example`、日志/错误规范、后端测试基线。

**退出条件**：空服务可在本地一致启动；迁移可重复；认证和角色在 API 层有自动化验证；任何密钥不进入 Git。

### Phase 4｜安全查询内核

**目的**：先建 SQL Policy 和受限执行器，再把 LLM 接到它前面。

**任务**：

1. 使用 `sqlglot` 实现 SQL AST 解析与规范化；
2. 实现“单条语句、仅 SELECT/只读 WITH、禁止 DDL/DML/事务/外部访问”的规则；
3. 实现 Schema/表/列白名单、角色允许对象和不可移除的工作区/行范围条件；
4. 实现强制 LIMIT、`statement_timeout`、最大行数/结果大小和可取消执行；
5. 区分候选 SQL、规范化 SQL、最终执行 SQL 和策略决策；
6. 建立安全测试矩阵：写操作、多语句、注释绕过、递归/无界查询、越权对象、跨工作区访问、超时。

**交付物**：`backend/.../sql_policy/`、只读 Query Runner、策略审计模型、安全测试集与拒绝原因规范。

**退出条件**：所有禁止 SQL 被可靠拒绝，数据库只读角色作为第二道防线同步生效；允许 SQL 能执行并留下完整策略记录。

### Phase 5｜Vanna 受控接入与证据链

**目的**：在已经安全的执行边界上接入 Vanna，使自然语言查询可控且可解释。

**任务**：

1. 固定 Vanna 版本/commit，记录依赖和上游许可证；
2. 配置可切换的 OpenAI-compatible LLM 提供方，审计模型、温度、Prompt/上下文版本；
3. 将工具面控制在：指标查询、Schema 查询、安全 SQL 执行、图表生成；设置最大工具循环次数；
4. 按用户角色只注入允许的 Schema、指标和示例，避免全量 Schema 暴露；
5. 实现“问题 → 工具调用 → 策略执行 → 表格/图表/总结”的 SSE 适配；
6. 将 SQL、指标定义、数据来源、关键结果和图表元数据组装为统一 Evidence 对象；
7. 覆盖正常、歧义、无权限、策略拒绝、无结果、工具失败等后端集成测试。

**交付物**：Agent 工厂、受控 Tool Registry、SSE Chat API、Evidence Schema、端到端后端演示和测试。

**退出条件**：核心问题能产生有证据的回答；任何 Agent SQL 都必须经过 Phase 4 的策略层；失败状态不编造结论。

### Phase 6｜前端分析体验

**目的**：把可信查询能力包装为可演示、可理解的分析产品。

**任务**：

1. 创建 `frontend/`，以 TailAdmin 为 MIT 合规基座，保留开源说明；
2. 建立页面信息架构：经营概览、智能分析、查询历史、指标口径、数据集、评测中心；
3. 在“智能分析”页封装 Vanna `<vanna-chat>`，配置认证和 SSE endpoint；
4. 实现结果证据抽屉/详情区：自然语言结论、指标口径、SQL、来源、表格、图表、耗时和策略状态；
5. 实现基础登录态、角色状态、加载/错误/空结果和响应式体验；
6. 为核心交互编写前端单元测试和关键路径 E2E 测试。

**交付物**：可运行 Next.js 分析后台、Vanna 集成、审计/指标页面、前端测试。

**退出条件**：用户可在浏览器完成“提问 → 观察流式过程 → 查看 SQL 与证据 → 回看历史”的闭环；前端不能绕过后端策略。

### Phase 7｜审计、权限与管理闭环

**目的**：把一次演示提升为可管理的内部分析系统。

**任务**：

1. 完成会话/消息历史、查询审计详情和筛选；
2. 完成指标定义、数据集版本和评测用例的最小管理界面/API；
3. 演示 `analyst` 与 `admin` 的权限差异，并写入审计；
4. 补齐数据版本、指标版本、模型版本和策略版本的关联；
5. 设计并验证数据保留/脱敏展示策略。

**交付物**：审计历史、最小管理能力、权限演示脚本、版本关联记录。

**退出条件**：任一回答都能按用户、时间、数据/指标/模型/策略版本追溯；权限差异可自动化证明。

### Phase 8｜评测、安全回归与性能基线

**目的**：用证据证明系统不是“偶然演示成功”。

**任务**：

1. 将评测草案扩展到至少 60 个版本化用例；
2. 建立 SQL 执行成功率、口径正确率、图表适配率、安全拦截率、P50/P95 时延等指标口径；
3. 编写评测 Runner，保存模型/Prompt/Schema/指标/数据版本与结果；
4. 对模型、Prompt、上下文规模和 SQL 策略进行受控对比；
5. 将安全用例和关键业务用例接入回归测试；
6. 记录已知失败模式与系统边界。

**交付物**：评测数据、Runner、报告模板、回归测试、性能基线与已知限制清单。

**退出条件**：所有安全攻击用例 100% 被阻断；核心问题有人工核验的结果；所有外部性能/准确率表述均可回放。

### Phase 9｜交付、部署与作品集整理

**目的**：形成可运行、可复现、可演示且可写入简历的完整项目。

**任务**：

1. 容器化或提供清晰的一键本地启动方案；
2. 补齐 README、架构图、运行指南、数据与开源署名、演示账号/演示脚本；
3. 录制或编写 3–5 条高价值业务问题的演示流程；
4. 由评测报告反推简历项目描述，只陈述可验证的技术和量化结果；
5. 进行从空环境启动到浏览器演示的验收。

**交付物**：可复现项目、演示材料、部署文档、最终评测报告、简历项目要点草案。

**退出条件**：陌生开发者可按文档启动；面试演示能清楚展示安全、指标、证据和评测，而非仅展示聊天页面。

## 5. 接口、数据与测试的前置设计

### 5.1 API 轮廓（在 Phase 3 冻结）

| 域 | 初步端点 | 责任 |
| --- | --- | --- |
| 系统 | `GET /api/v1/health` | 服务和依赖健康检查。 |
| 身份 | `GET /api/v1/me` | 当前用户、角色、可访问范围。 |
| 分析 | `POST /api/v1/chat/stream` | SSE 流式返回 Agent 状态、SQL、结果、图表与回答。 |
| 历史 | `GET /api/v1/queries`、`GET /api/v1/queries/{id}` | 查询历史、审计和证据详情。 |
| 指标 | `GET /api/v1/metrics`、`GET /api/v1/metrics/{id}` | 只读指标口径；管理接口只授予 admin。 |
| 数据集 | `GET /api/v1/datasets` | 数据版本、来源、加载状态。 |
| 评测 | `POST /api/v1/evaluations/run`、`GET /api/v1/evaluations/runs/{id}` | 仅 admin 可运行/查看完整评测。 |

SSE 事件必须使用稳定类型，例如 `status`、`tool_call`、`sql_candidate`、`sql_policy`、`table`、`chart`、`answer`、`error`、`done`；每个事件携带 `request_id`，便于前后端和审计关联。

### 5.2 数据资产版本规则

- `dataset_version`：标识原始来源、许可证、下载/转换版本与 checksum；
- `schema_version`：标识 DDL 与字段字典版本；
- `metric_version`：标识业务口径版本；
- `policy_version`：标识 SQL 规则配置和执行器版本；
- `model_run_version`：标识模型、模型参数、系统 Prompt 与上下文版本；
- 每条 `query_audit` 必须关联上述适用版本，不能只记录最终文本答案。

### 5.3 测试金字塔

| 层次 | 重点 | 典型对象 |
| --- | --- | --- |
| 单元测试 | 快速、无外部依赖 | SQL AST 规则、指标定义校验、证据装配、权限判断。 |
| 数据测试 | 数据质量与口径 | 主外键、空值、时间范围、指标 golden SQL、转换结果。 |
| API/集成测试 | 服务边界 | 鉴权、只读执行、SSE 事件顺序、审计写入。 |
| Agent 评测 | 生成与业务正确性 | 标准问题、标准 SQL/结果、歧义问题和失败行为。 |
| 安全回归 | 不可退化的底线 | 写 SQL、多语句、越权、无界/超时查询。 |
| E2E | 用户关键路径 | 登录、提问、查看证据、查询历史、admin 管理。 |

## 6. 关键决策检查点

下列事项必须在对应阶段明确记录为 ADR；未决时不得靠临时实现掩盖：

| 检查点 | 最迟确定阶段 | 需要做出的决定 |
| --- | --- | --- |
| Vanna 接入版本 | Phase 3 前 | PyPI 版本是否满足当前 API；若否，固定哪个 Git commit。 |
| LLM 提供方 | Phase 5 前 | 开发/演示用模型、预算、密钥管理、故障回退与审计字段。 |
| 认证方案 | Phase 3 前 | 本地演示身份、JWT/会话边界、角色及工作区范围。 |
| 权限粒度 | Phase 1 前 | 仅表/列权限还是增加 workspace 行级范围；最小演示数据如何表达。 |
| 指标口径 | Phase 1 | 每项业务定义、分母、时间字段、退款/取消规则和维度限制。 |
| 前端复用范围 | Phase 6 前 | TailAdmin 复制的页面/组件范围、许可证声明和 Vanna Web Component 封装方式。 |
| Redis 是否引入 | Phase 7 后按需 | 只有出现量化的缓存、限流、异步任务或多实例需求才立项。 |

## 7. 风险、缓解与降级方案

| 风险 | 缓解策略 | 降级方案 |
| --- | --- | --- |
| LLM SQL 不稳定 | 小工具面、指标上下文、少量高质量示例、离线评测、低温度。 | 返回“需要澄清/无法可靠生成”的受控失败，而不猜测。 |
| SQL 策略误拦截合法查询 | AST 测试矩阵、审计策略原因、白名单配置版本化。 | admin 审核策略配置，绝不绕过只读数据库权限。 |
| 业务口径不清 | Phase 1 先冻结数据字典和指标目录。 | 明确展示假设或要求用户澄清。 |
| 公开数据许可证/体量问题 | manifest、署名、原始数据不入库、合成 fixture。 | 用 Chinook/合成数据维持回归与演示。 |
| 上游 Vanna API 变化 | 固定依赖版本/commit，记录上游接口。 | 通过本项目 Agent 适配层隔离上游调用。 |
| 前端集成复杂 | 把 Vanna Web Component 封装在单独 client component，SSE 契约先测试。 | 先用独立分析页验证，不阻塞经营看板。 |
| 项目范围膨胀 | 阶段门、明确不做项、ADR 和评测优先。 | 延后 Redis、多租户、导出、RAG 和多数据源。 |

## 8. 每轮迭代的工作包模板

每个开发迭代必须是可验收的小闭环，建议遵循：

```text
输入：本轮目标、对应 Phase、验收条件、已知风险
实施：限定范围内的代码 / 数据 / 文档 / 测试
验证：测试命令、测试结果、人工核验或评测结果
文档：PROJECT.md + 相关 docs + 飞书迭代记录
版本：单一主题 Commit + GitHub 推送
输出：完成项、证据、commit SHA、飞书位置、下一步与未决项
```

建议的首批工作包顺序为：

1. Phase 1：数据合同与指标目录；
2. Phase 2：PostgreSQL 与可复现数据管道；
3. Phase 3：FastAPI / 迁移 / 演示身份；
4. Phase 4：SQL Policy 与安全回归；
5. Phase 5：Vanna 受控查询与证据链；
6. Phase 6：Next.js 智能分析页与看板；
7. Phase 7–9：管理闭环、评测、交付。
