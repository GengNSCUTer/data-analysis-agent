# Introduction

![Status: Planned](https://img.shields.io/badge/status-Planned-blue)

本轮是代码核查和实施设计，尚未新增运行时能力。它承接四周学习计划的 Day 3，不启动
后训练、重新构建数据集或重做会话架构。目标是用少量通用计算覆盖常见经营分析问题，
让模型理解问题和组织解释，服务端负责计算与事实结论；不为每种中文句式添加拦截规则。

最小任务卡：输入为用户意图、已验证 QueryPlan、Catalog 和完整 ResultArtifact；输出为
能力缺口、查询覆盖表、计算语义及分步验证方案。保持身份隔离、SQL 安全、结果预算和
可信工件边界。当前验收采用代码追踪与合成数据复现；后续实施再执行单元、数据库和浏览器测试。

**已核实的缺口。** `result_evidence.py:build_result_evidence()`目前提供概览、选行、
可加指标求和和两行比较。时间证据只有首末行，没有逐期比较、期间完整性或分组趋势。
`followup_adds_numbers()`只检查新数字，不能证明数字属于正确指标或文字趋势正确。
2026-10-23 用合成月数据 `100 → 120 → 110 → 150` 调用现有代码：证据没有趋势字段；
“每个月都增长”与“订单数量最高为150”均未被新数字检查拒绝，尽管前者有反例、后者错用了 GMV。
这是定向缺陷复现，不是线上准确率测试。

首次查询通过 `llm_observability.py:_explain_result()`解释结果；追问通过
`chat_runtime.py:_inspect_previous_result()`读取完整工件。仅给追问增加算子会漏掉
“第一次就问全年是否逐月增长”的情况，二者必须复用计算路径。

## 1. Requirements & Constraints

- **REQ-001**: 计算读取完整已验证工件或本轮完整 DataFrame，不读取前端200行预览或模型样本；完整工件仍只代表原查询范围。
- **REQ-002**: 区分业务数据覆盖、时间覆盖和模型证据行覆盖。模型只看到部分行，不妨碍服务端对完整结果作计算；完整返回Top-10也不代表全部业务。
- **REQ-003**: 继续使用现有语义解释调用提出受限计算参数，首次问题和追问共用计算实现，不增加固定关键词路由或每轮第二个意图模型。
- **REQ-004**: 每项计算产出指标、单位、筛选、时间、分组、分子/分母或比较对象、缺失情况及结论。事实结论由服务端生成，不能仅用“数字已经出现过”作为支持证明。
- **REQ-005**: 能用当前结果回答就直接回答；缺少可查询的列或期间时复用普通SQL路径补查；仅真正歧义才澄清。缺月只影响需要连续月份的判断，不阻断极值等其他问题。
- **REQ-006**: SQL返回结果口径错误仍可能导致分析错误；计算正确不替代QueryPlan检查、SqlPolicy、reader和ResultValidator，也不宣称证明任意SQL业务正确。
- **REQ-007**: 组合问题可提出多个受限计算请求，共享同一完整数据与预算；“列出前十、计算份额并画图”不能只回答第一部分。普通SQL查询能力不受这些结果算子枚举限制。
- **SEC-001**: 工件读取沿用用户/workspace/版本和权限校验。权限拒绝或工件完整性失败不能伪装成“数据不足”后自动绕过。
- **SEC-002**: 不向模型开放Python、任意表达式、文件路径或数据库权限。新增补查仍经过现有完整查询执行链和预算。
- **CON-001**: 不新增数据库表、hash、冻结contract、独立Agent或通用公式DSL；内部接口直接更新全部调用方和测试，不加兼容别名。
- **CON-002**: 本方案覆盖描述性分析；预测、因果归因、显著性检验、用户漏斗/留存及未定义的业务指标不由结果样本推断。
- **GUD-001**: 不把所有统计塞给模型。按当前问题优先提供所需计算、反例和范围说明，再使用剩余token提供行与一般统计；不以缺少无关信息为由追问。

### 查询覆盖与数据要求

表中“补查”指按已有Catalog与用户已确认范围执行普通只读查询，不是让用户重新说一遍
已有条件。“已有”只描述实际实现，不代表对应业务语义已完整验证。

| 查询类别与例子 | 目前情况 | 服务端应提供的依据 | 结果不够时如何处理 |
| --- | --- | --- | --- |
| 查询/下钻：“最高州内哪些品类卖得好”“按月和品类看订单” | 有受控状态、实体引用及SQL路径 | 从可信结果解析父实体，保留已确认指标/筛选/时间，再按新维度查询 | 新分组走QueryPlan和SQL，不把未知品类数据从州级结果推断出来 |
| 明细/定位：“第9、10名是什么”“最后一个月呢” | 有选行；端点有基础证据 | 完整工件中的对应行、实体、期间及原查询范围 | 新维度或未返回实体才补查；不把展示位置冒充业务排名 |
| 汇总：“这250行总额多少” | 有受限求和 | 允许跨当前维度相加的指标合计、有效/空值数、总体范围 | 去重计数重叠、均值和比率总体口径走原始事实重算 |
| 趋势：“一直上涨吗”“连续下降几个月” | 尚无趋势计算 | 按实体排序的逐期差额、涨跌平次数、最长连续段、首个反例及完整性 | 缺粒度/期间时利用已确认状态；真缺基线才澄清；缺数据返回可知事实与缺口 |
| 累计/平滑：“今年累计多少”“最近三个月均值” | 无通用累计或滑窗计算 | 按日历累计可加指标；固定窗口的序列均值注明窗口与有效期间 | 未返回全年不能说全年累计；月客单价简单均值不是三个月整体客单价，需权重或补查 |
| 期间比较：“环比/同比多少”“去年同期呢” | 仅有任意两行比较 | 同口径对齐期间、绝对变化、相对变化及比较资格 | 缺基期补查；未完整月与完整月不可默认等价；不同币种不可直接比 |
| 排名：“增长最快的品类”“每个月前三名” | SQL支持Top-N；结果计算尚未统一 | 对实际请求的数值或变化量排序、分区、并列规则、有效比较数 | 增长排名需要各实体基期与本期；缺基期补查，不退化成金额排名 |
| 占比/集中度：“前十占全店多少”“前两类占这些结果多少” | 未实现统一占比 | 明确分子、分母、范围、可加性；可计算返回集合内累计占比 | Top-10没有全店分母就补查；重叠分组不能简单相加 |
| 多层汇总：“按月按州的结果合成全年总额”“全店客单价” | 有可加性检查，无通用重聚合 | 可加指标按合法分组折叠；总体比率/均值由分子分母重算 | 仅有各州客单价不能平均成全店客单价；缺权重重查 |
| 分布/阈值：“哪些州低于一万”“中位数多少”“有几个月下跌” | 未实现统一计算 | 目标群组筛选、计数、中位数/分位数、明确定义的比较运算 | 月总额只能说明月分布，不能回答订单金额分布；需要明细或数据库聚合 |
| 波动/贡献：“哪次下跌最大”“哪个品类贡献了增量” | 尚无专项计算 | 逐期最大跌幅；可加且互斥分组的实体增量及总体净增量 | 增量贡献率遇总体净增量为0不计算比率；仅说明数值分解，不声称业务原因 |
| 结果展示：“换柱状图”“导出”“只看SP” | 有图表、工件与筛选路径 | 同一授权结果的确定性变换，保持指标和筛选语义 | 原结果没有SP明细或新图需要新分组才补查；不因换图自动重查 |
| 定义/建议：“GMV口径”“该关注什么” | 有免查询解释路径 | Catalog定义或标明为建议的通用知识 | 没有实时数据不声称“目前经营变差” |
| 原因/预测/漏斗：“为什么下降”“预测下月”“复购率” | 不具备通用支持 | 已有维度可作描述性拆解；明确所需事件、观察窗口、方法和缺失数据 | 不把相关性当因果；无指标与方法时说明限制，不拼造新口径或预测 |

### 趋势判断的具体语义

对于完整自然年的单个按月序列，先确定业务日历、时区、起止区间和月份键，再核对12个月
及11个相邻月变化。按月是日历月份，不能用固定30天替代；周/月/季度/年沿用SQL分桶的
日历定义。查询从月中开始或结束时记录部分期间，不默认等价于完整月。

| 说法 | 可验证定义 | 必须避免的误判 |
| --- | --- | --- |
| “每个月都增长”“持续上涨” | 指定期间内每个相邻完整月都严格大于前月 | `100,120,110,150`期末较期初增加50%，但3次变化中有1次下降 |
| “从未下降” | 同一序列每个相邻变化均大于等于0 | 持平可满足不下降，但不满足严格增长 |
| “期末比期初高” | 比较指定首期和末期；输出差额及合法的变化率 | 不能改写为持续增长，也不等同于统计显著的上升趋势 |
| “走势怎么样” | 列出首末变化、涨跌平次数、峰谷与连续段 | 波动中净增只描述为期末高于期初，不用一个标签掩盖中间反转 |
| “SP和RJ谁增长更稳” | 每个州单独检查同一日历期间；v1提供各自涨跌与连续段 | 不把按州×月的所有行串成一条序列；“稳”无指定统计定义时解释所用描述，不发明显著性 |

趋势判断使用“成立/不成立/证据不足”三种结果。缺月、NULL、非数值和重复期间分别记录，
不能静默丢掉、补0或把重复月份相加。发现一个有效相邻月下跌就足以否定“全部严格增长”；
若所有可观察变化均为正但存在缺月，只能说证据不足。单个观测点没有增长变化可比较。

数据缺行不自动说明零交易：只有业务数据覆盖和指标定义明确支持无记录为0，查询才可按
日历补0；否则报告缺失。按月Top-N中的某品类消失，可能是掉出前N，不可推断销售为0。
日、周、季度、年沿用相同算法，期望期间由实际范围和日历生成，不写死月份个数。

### 比较、占比与重聚合的共同边界

金额变化为本期减基期；正基数的相对变化为差额除基期。零基数输出差额但变化率无定义；
负基数默认只报告差额并解释限制，不按正基数惯例宣称增长率。比率从10%到15%是增加
5个百分点、相对提高50%，两者分别标注。金额、计数、比率和均值由Catalog明确单位与
存储尺度，不用数值恰好位于0到1之间猜测它是不是比例。

同比按相同日历期间对齐，环比按相邻期间对齐；完整性及时间字段口径必须一致。涉及闰日、
ISO周或当前未结束期间时显示实际比较窗口；v1默认不做完整性不一致的整期增长率，用户
明确要求等长截至日比较才使用对齐窗口。多个事实域的时间归属不同，不因列名都叫time而混比。

“这些结果内占比”可以用合法的完整返回集合做分母；“全店占比”需要同口径全店分母。
分子分母都要有明确范围和正的合法分母。跨品类去重订单数、客户数等多重归属指标不能
相加；GMV可加也只在获准维度、过滤和币种内成立。客单价必须由金额和有效订单数按原
定义计算；不能用各组客单价的简单平均代替。阈值筛选后的群组数不能说成原始订单数。

### 运行时组织与回答依据

```text
用户问题 + AnalysisState + 当前可信结果范围
    -> 现有语义解释器提出计算请求或普通查询意图
    -> 服务端判断当前结果能否提供所需列、期间、口径和总体
       -> 足够：读取完整授权工件，执行受限计算
       -> 缺少可查数据：普通QueryPlan -> SQL检查与执行 -> 同一计算器
       -> 真正歧义：只问缺失部分；不可支持：说明缺少的数据或方法
    -> 服务端生成事实结论与范围说明
    -> 必要时模型结合事实解释；表格和图表仍使用原可信工件
```

沿用 `ResultInspection` 并扩展少量有类型操作：现有 `overview/rows/sum/compare`，新增
`trend/period_compare/rank/share/distribution/threshold`。不接受任意公式或Python。
字段按操作需要提供指标、实体分组、日历期间、比较对象、排名方向与并列模式、分母范围
及阈值；不能让LLM提供“计算结果”。实体来自现有可信引用解析，不靠模型猜行号指代州。
组合请求把现有单个`SemanticIntent.result_inspection`直接改为`result_inspections`列表，
更新全部调用方和测试，不同时保留新旧字段；每项使用同一`ResultInspection`类型。累计与
固定窗口序列均值作为trend的显式模式，明确窗口长度与单位，不引入任意程序执行。

新增 `result_analysis.py:analyze_result()`纯计算入口，返回具名的四类处理结果：
`ready`、`query_required`、`clarification_required`、`unsupported`。权限异常仍独立抛出。
数据有缺口但能给部分事实时为ready并标明结论证据不足，不把所有内容都拒绝掉。补查沿用
现有一次候选修复预算；不能因真实缺月而反复查询，也不能静默扩大用户筛选或时间。

运算遵守现有结果行数、字节与超时预算。工件内计算复用同一完整DataFrame与分组结果，
不为每个子问题重新读CSV；全店分母、大量明细的分布或更粗粒度汇总优先让PostgreSQL
返回聚合结果，不为取得完整依据把数百万事实行搬到应用或模型。计算证据仍受4K预算，
前端预览仍为200行；两者都不用于截断服务端实际计算总体。

计算证据至少绑定 `operation/metric_id/unit/scope/operands/coverage/findings`。coverage
分别表达当前返回集合、期望时间和模型可见行；findings含服务端判定、计算值、观察数量与
必要反例。复用工件ID、状态版本和现有trace记录，不加新hash。

关键结论用服务端模板直接呈现，例如“不是逐月增长：3月为110，低于2月120”。模型可
解释含义和给出有区分的建议，但不负责重新计算、改写判定或把一个指标的数挪给另一个。
简单计算不需要额外模型调用。仅让LLM自由输出再查数字，无法保证文字结论正确；v1不
宣称能验证所有自由文本，普通自由叙述的语义审核仍是局限。

## 3. Alternatives

- **ALT-001**: 把完整结果都塞给LLM心算。未采用：上下文与隐私预算仍存在，且完整可见不能保证逐期、比率或总体判断正确。
- **ALT-002**: 每种问法加入中文正则或硬性澄清。未采用：同一计算可有许多表达，重复语言闸门会恶化连续对话；限制只施加在数据与运算能力上。
- **ALT-003**: 允许模型执行任意Python或通用公式。未采用：当前算子足以覆盖已识别需求，不为扩大表达能力引入沙箱和代码审计负担。
- **ALT-004**: 再调用一个LLM裁判审核所有答案。未采用：延迟和费用增加，裁判同样可能心算或语义误判；确定性运算与事实呈现先解决可计算问题。
- **ALT-005**: 遇到缺数据全部拒绝或每轮重查。未采用：可知结论应正常回答；仅缺查询数据时补查，避免反复澄清、额外扫描和真实缺失下的循环。

## 6. Testing

- **TEST-001**: 趋势反例：完整12月严格上升判成立；含一次下降判不成立并准确定位；仅持平不满足严格增长但满足不下降；首末增加不冒充逐期增加。
- **TEST-002**: 覆盖不全：缺中间月/首月/末月、NULL、空集、单点、重复月分别有预期。缺月但有有效相邻下降可否定严格增长；缺月且已知都上涨仍不得肯定全年上涨。数据缺失不得自动补0。
- **TEST-003**: 日历：乱序、时间别名、时区、闰年、跨年ISO周、季度和部分期间；重排行不改变按时间计算；按服务端分桶日历生成期间，不用固定天数替代月。
- **TEST-004**: 分组：两个州方向相反、某州缺月、按月Top-N成员变化；逐组分析互不污染，Top-N未出现不算0，缺月不阻断同一结果的极值/选行。
- **TEST-005**: 比较：正/零/负基数、相同金额、10%到15%的百分点与相对变化、缺同比基期、未结束月；避免用当期金额代替增长排名。
- **TEST-006**: 排名：升降序、并列、第N边界、空值、每月×州分区、同比排名；默认精确N并稳定破同分，明确要求并列时可超过N且遵守预算。
- **TEST-007**: 分母：Top-10内占比与全店占比不同；全店分母缺失走补查；互斥GMV可加、跨品类去重订单不可加；客单价需要权重；分母0、总体净增量0及空值不伪造比例。
- **TEST-008**: 分布/阈值/滑窗：群组中位数、分位数插值、阈值等于边界、金额单位与比率尺度、空值数量；月结果不可回答订单分布，群组命中数不可冒充订单数。累计不得跨缺月冒充完整期；三个月窗口不能按最近三条观测代替，月客单价序列均值不能冒充总体客单价。
- **TEST-009**: 结论：错误“每月都增长”、错把GMV说成订单数、把10%到15%说成增加5%、局部份额冒充全店；核对用户看到的服务端结论与对象绑定，不能只断言答案里有数字。
- **TEST-010**: 接线与性能：首次/追问同一运算结果一致；完整工件可算时SQL次数不增加，缺基期只补需要的查询；跨用户/版本失效拒绝；保留已确认条件；4K证据优先保留计算结论；组合问题同时完成排名、份额与图表，不能静默遗漏子问题；在既有行数/字节预算内测最大分组量与耗时。
- **TEST-011**: 受控浏览器连续链路：全年月走势→是否逐月增长→首次下跌与幅度→同比缺基期补查→各州增长排名→前十内占比→全店占比补查→阈值筛选→仅换图→刷新后继续解释。检查每步参数、计算、实际SQL数和最终文字。
- **TEST-012**: 在线模型在Olist/TheLook各执行一条多轮开发对话，覆盖趋势、比较、排名、占比、比率总体、缺数据、图表和刷新；逐题用独立SQL/手算期望核对，并区分模型理解失败、SQL口径错误、计算错误和解释错误。不能预先宣称全部通过。

## 7. Risks & Assumptions

- **RISK-001**: SQL本身可能口径错误，完整工件只保证所保存结果未被截断，不证明所有业务事实正确；沿用现有检查，异常按实际问题修复。
- **RISK-002**: Catalog目前没有完整的单位/日历/分子分母计算语义；只补操作确实需要的信息，不能根据数值形状或指标名字猜测。
- **RISK-003**: 硬性要求每种分析都具备完整日历、权重或全店分母会再次破坏流畅度；校验必须按当前请求检查，能回答部分事实时正常回答并标注缺口。
- **RISK-004**: 自由语言的因果、趋势和对象归属不能由数字集合检查保证；本轮保证的是服务端呈现的指定运算事实，不是任意LLM文本的完全语义证明。
- **ASSUMPTION-001**: v1继续支持单进程、自托管PostgreSQL分析Copilot，Olist和TheLook复用同一实现，以配置和Catalog表达业务差异。
